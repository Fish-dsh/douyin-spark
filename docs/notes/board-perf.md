# 板端性能：一夜 6 分半慢在哪

板子：Orange Pi Zero3 / 4 核 A53 / 1483MB / Debian 12 / Xvfb `:99` 800x600 软渲染（单核约为开发机的 1/10）。生产：2 个账号、每晚约 8 个待续好友。

## 三代数据

| 时间 | 总耗时 | 人均 |
|---|---|---|
| 会话 51 之前 | **21m46s**（9 人） | 138s |
| 2026-11-18 | **5m44s**（3+5 人） | — |
| 2026-11-19 | **6m29.8s**（3+5 人） | — |

会话 51 砍掉「每个好友都重新 goto 一次」并跨好友复用页面，人均 138s → 27s，**约 5 倍**，是这项目唯一一次数量级优化。

## 6m30 怎么拆的

两个账号只差在人数，做边际法：差 54.2s / 差 2 人 = **边际 27.1s/人**；每账号固定开销 167.8 − 3×27.1 = **86.5s**（用 5 人那个账号验算同为 86.5s）。

```
6m30 ├── 固定 173s（每账号开一次机）   45%
     │     chromium 冷启动 + storage 恢复 / goto 整页 / 列表填充
     └── 逐人 217s（8 × 27.1s）        55%
           打开会话 / 点表情 / 等面板关闭 / 文字确认
```

只有两个观测点，两点必然拟合一条直线，所以 45% 只能当**方向判断**，不是实测结论——真正构成看下面那两行计时。

## 天花板的实话

- **调等待参数**：真人固定睡眠 3.35s/人 + 拟人间隔 0.5–1.2s。但其中「等抖音自己缓过来」的那几个不能动，真能安全省的只有表情确认轮询 1–2s/人 → **8–16s/夜（2–4%）**。这条到顶了。
- **少开机、少整页加载**：唯一还能一块一块算的收益，会话 51 的 5 倍就是砍的这个。
- **Chromium 用 GPU**：已冻结，见 [board-gpu.md](board-gpu.md)。

## 这轮改了什么（会话 56）

**发现阶段的页面不再扔掉，直接交给发送阶段。** 原来是扫完列表就 close，发送阶段再从零开一次浏览器、重新加载整页。现在发现一旦有待续好友，就把 `(browser, context, page)` 交出去，第 1 个好友直接在这张页面上发——`process_friend` 本来就会先判页面就绪去跳过整页 goto，所以省的正是 **一次冷启动 + 一次整页加载 + 一次列表填充**。页面不可用就丢弃重建，不硬用。

估 30–50s/账号、一夜 70–100s；这是估算，板端还没跑过新代码。

**顺手把「看不见的那 27 秒」拆开了**：

```
[timing] process_friend(名字) 耗时 27.4s (打开页面 0.2s / 定位好友 1.1s / 打开会话 12.1s / 表情 9.4s / 文字确认 4.6s)
[timing] 会话建立 启动 18.3s / 建页导航 2.1s / 落地就绪 6.7s(合计 27.1s)
[timing] 会话列表就绪 41.2s (已就绪)
```

后两行加起来就是 86.5s 的构成，只是 `time.monotonic()` 差值，没改任何就绪判据。

## 今晚看两个数字

板端 `runtime/spark.log`：`[perf] 沿用发现阶段的会话页面` 应出现 **2 次**（0 次 = 交接被判不可用，等于白改）；`[timing] 会话建立`+`[timing] 会话列表就绪` 各 **2 次**，把四段数字记回本文件——下一轮选哪条路就看它。

总耗时该从 6m30 掉到 5m 上下。**回滚**：revert 一个提交，交接是纯增量，发送判据（表情面板关闭＝成功）一行没动。

## 还能试的（按性价比）

| 候选 | 预估 | 风险 |
|---|---|---|
| 单 Playwright + 单 Browser + 每账号独立 Context（只共用浏览器进程，不共用 Context/Cookie） | 省 1 次冷启动 ≈ 20–30s/夜 | 中：要验两账号登录态互不污染、一个异常退出不影响另一个；做不到就保持两个进程 |
| 减少 SPA 自身重复初始化（不是缓存 DOM 节点，那个必错；是复用「已验证的页面状态」） | 未知，需先测 | 低—中：不碰协议、不碰验证码 |
| 表情确认轮询合并往返（只能少取值次数，判据不动） | 8–16s/夜 | 中 |
| 精简 `LAUNCH_ARGS` 里对离线板子无效的开关 | <5s | 低，顺手 |
| ~~降低真人固定睡眠~~ | 最多 27s/夜 | 高，直接换漏发率 |

顺序：**先看上面两个数字 → 验证交接收益 → 再决定动哪个**。一次只改一个变量。

## 别重走的路

- **原生 headless 替 Xvfb**：六组实测板端首屏渲染不出来，且不吃 Panfrost。
- **持久 profile**：实测仅 4.4s，还得重做多账号隔离。
- **连图片字体一起拦**：三档实测 RSS 都是 1281MB，对内存零收益，且是很强的机器人特征。

## 外部评审（ChatGPT，11-19）

把上面这套数据同步给它之后，它指出三处我认了：两点边际法不足以证明固定开销恒定（已降级为方向判断）；固定开销最大头可能是 goto 后的 SPA 初始化而非冷启动（已加三阶段计时去测）；等待优化天花板是 2–4% 不是 7–9%（已改口径）。另外两条建议已进候选表：A 改成「单 Browser 独立 Context」、以及「减少 SPA 重复初始化」。

它那句话我接受：**别把「6m30 压到 5m30」当目标，长期无人值守的稳定性才是要的东西**——所以判据没为性能让过一步。
